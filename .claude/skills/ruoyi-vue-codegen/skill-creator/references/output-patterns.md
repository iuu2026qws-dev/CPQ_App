# 输出格式和质量标准模式

## 模板模式

### 当技能需要生成标准化文档时

提供一个清晰的模板，包含：
- 必需的章节/字段
- 建议的格式和结构
- 示例填充内容

```markdown
## 输出格式

### 报告结构
1. 执行摘要（300-500 字）
2. 详细分析（1000-2000 字）
3. 建议（500-800 字）

### 模板
\`\`\`markdown
# [标题]

## 执行摘要
[核心发现概括]

## 详细分析
### [分析维度 1]
[内容]

### [分析维度 2]
[内容]

## 建议
1. [建议一]
2. [建议二]
\`\`\`
```

## 示例模式

### 当技能需要展示正确输出格式时

提供好的和坏的对比示例：

```markdown
## 输出示例

### ✅ 好的输出
\`\`\`markdown
## API 端点设计

### POST /api/users
创建新用户。

**请求体：**
- `name` (string, required) — 用户名称
- `email` (string, required) — 邮箱地址
\`\`\`

### ❌ 差的输出
\`\`\`markdown
## 用户 API
POST /api/users - 创建用户
参数：name, email
\`\`\`

关键区别：
- 好的输出包含类型、必填标记和描述
- 差的输出缺少关键信息
```

## 检查表模式

### 当输出质量需要系统性验证时

```markdown
## 质量检查清单

在完成输出前，确认以下几点：

- [ ] 所有代码示例都可以正常运行
- [ ] 没有使用"容易"、"简单"等主观描述
- [ ] 所有链接都是描述性的（不是"点击这里"）
- [ ] 标题清晰表达了要点
- [ ] 复杂概念有具体示例说明
- [ ] 格式一致（缩进、空行、标点）
```

## 增量输出模式

### 当输出内容较多时

分阶段输出，避免一次输出过多信息：

```markdown
## 输出策略

### 第一阶段：概览
先输出高层总结和关键发现（500 字以内），让用户快速理解整体情况。

### 第二阶段：详细分析
如果用户需要更多细节，再逐节输出详细分析。

### 第三阶段：深度内容
针对用户特别关注的维度，提供深度分析。

**指导原则：**
- 先问用户是否需要全部详细内容
- 每部分内容控制在 2000 字以内
- 使用"查看更多"引导用户按需获取
```

## 多格式输出模式

### 当需要生成多种格式时

```markdown
## 输出格式要求

### Markdown（源文件）
- 保存至 `docs/xxx.md`
- 包含完整内容和元数据

### HTML（可浏览格式）
- 从 Markdown 转换生成
- 保存至 `docs/html/xxx.html`
- 包含基础样式，可独立打开

### JSON（机器可读格式）
- 保存至 `data/xxx.json`
- 结构化的关键数据
- 用于程序化处理
```

## 命名和路径约定

### 文件命名
- 使用描述性名称：`功能需求文档.md` 而非 `doc1.md`
- 使用连字符分隔英文：`api-reference.md` 而非 `api_reference.md`
- 避免特殊字符和空格

### 目录结构
```
project-root/
├── docs/          # 文档输出
│   └── html/      # HTML 格式文档
├── prod/          # 原型和设计输出
│   └── html/      # HTML 原型
└── index.html     # 统一索引文件
```

## 一致性标准

### 术语一致
- 选择一个术语后全程使用
- 例如：始终用"用户"而非混用"使用者""顾客""客户端"

### 格式一致
- 表格对齐
- 序号格式统一
- 代码块语言标注一致

### 图标使用一致
| 图标 | 含义 |
|------|------|
| 🔴 | 高优先级/严重 |
| 🟡 | 中优先级/警告 |
| 🟢 | 低优先级/正常 |
| ✅ | 已完成/正确 |
| ❌ | 未完成/错误 |
| ⚠️ | 需要关注 |
| ⭐ | 亮点/推荐 |
