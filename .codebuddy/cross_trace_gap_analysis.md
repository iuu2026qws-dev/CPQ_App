## 零、重大发现：技术栈不一致

**这是本次追溯发现的最严重问题。**

| 层面 | 阶段三(技术实现层) | 后端设计 + 开发计划(实际) |
|------|:---:|:---:|
| 后端语言 | Go 1.23+ / Hertz + Kitex | Java / Spring Boot (RuoYi-Vue-Plus) |
| 数据库 | PostgreSQL 16 | MySQL 8.0 |
| 前端框架 | React 19 + TypeScript + Ant Design | Vue 3 + Element Plus |
| 部署 | K3s + Rancher | Nginx 反向代理 |
| ORM | GORM v2 | MyBatis-Plus |
| 多租户 | PG RLS + Multi-Schema | MyBatis TenantLine 拦截器 |
| 搜索引擎 | MeiliSearch | 无 |
| 消息队列 | NATS + Apache Pulsar | 无 |
| 缓存 | Redis 7.4 Cluster | 无独立缓存规划 |
| CI/CD | GitLab CI + ArgoCD | 未规划 |

**影响**：阶段三的 15 个微服务分解、70 个 API 端点、43 张表（PG 类型 UUID/BOOLEAN/JSONB/TIMESTAMPTZ）、8 个 View（含递归 CTE）、4 个存储过程、CSP 求解器池化设计、HPA 弹性伸缩、K3s 私有化部署方案——全部基于 Go/PG 栈。实际开发的 Java/MySQL 栈无法直接使用这些设计产出。

**建议**：决定保留哪个技术栈后，对另一个栈的设计文档进行同步更新，避免后续开发者混淆。

### 1.2 关键断层详情

**D1. ECN/ECO 工程变更 — 阶段一 P0 + 阶段二详细 → 阶段三无服务**

- 阶段一 §2.3 列为 P0（配置变更申请+影响范围评估）
- 阶段二 §1.2 有完整 9 步五级联动传播链（产品变更→BOM变更→报价影响→审批链重建→客户通知）和状态机
- 阶段三 15 个微服务中**没有 ECN 服务**，API 端点中也没有 ECN 相关端点
- 开发计划中也没有 ECN 模块

**D2. 销售赋能 — 阶段一 P0 → 全链路缺失**

- 阶段一 §2.3 P0：产品知识库基础版（2 功能点）
- 阶段二：无详细设计
- 阶段三：无对应微服务
- 前端设计：菜单 50086 知识库，但无页面设计规格

**D3. 数据迁移 — 阶段一 P0 + 阶段二详细 → 阶段三无服务**

- 阶段一 §2.3 P0：产品数据批量导入+校验（2 功能点）
- 阶段二 §1.3：五阶段时间线（预检→映射→试迁移→正式→五维对账）+ 回滚条件矩阵
- 阶段三：无 `migration-service`，API 端点中无迁移端点
- 开发计划：无数据迁移模块任务

**D4. 方案管理 + 售前协同 — 功能规格缺失**

- 阶段二未提供完整的 Function Spec（SLA/异常处理/接口契约），仅流程描述
- 阶段三虽有 S11/S12 服务，但无详细设计支撑
- 前端 SolutionEditor.vue 设计规格完整（§8.3），但后端 Service 设计脱节

## 七、建议优先级

1. **立即决策**：技术栈统一（Go/PG? 还是 Java/MySQL?），更新不一致的设计文档
2. **Sprint 3 增补**：ECN/ECO、售前协同、竞品对标基础 CRUD
3. **Sprint 4-5 补全**：向导式销售、方案编辑器、数据迁移
4. **Sprint 6+ 新增**：销售赋能知识库、消息队列、Redis 缓存
5. **持续跟进**：AI 能力（阶段二§6）、多工厂产能分配

当前开发计划仅覆盖阶段一 P0 功能的约 **60%**，阶段二详细流程的约 **5/7**，阶段三微服务的约 **10/15**。
